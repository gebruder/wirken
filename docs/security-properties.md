## OWASP Agentic AI Threats and Mitigations

Threat text is quoted verbatim from
[Agentic AI - Threats and Mitigations](https://genai.owasp.org/resource/agentic-ai-threats-and-mitigations/),
v1.1, December 2025, which numbers its threats T1 to T17. A row is here only
where a shipped mechanism addresses the threat as that text defines it;
T5, T7, T10 and T12 have no wirken control and are absent.

| TID | OWASP definition | Mechanism | Gap |
|-----|------------------|-----------|-----|
| T1 Memory Poisoning | "Memory Poisoning involves exploiting an AI's memory systems, both short and long-term, to introduce malicious or false data and exploit the agent's context. This can lead to altered decision-making and unauthorized operations." | Short-term memory is the per-session hash chain, replayed on wake, so a modified turn breaks its own chain. Long-term memory entries carry five origin labels stamped by the runtime from the turn's inbound context and unreachable from tool arguments, so a model cannot author its own provenance; a turn missing any of them writes no entry at all. Reading another channel's entries is Tier 3 and cannot be pre-approved. [enforcement-model.md](enforcement-model.md#cross-channel-memory), [audit-cli.md](audit-cli.md) | Provenance is recorded, not validated: the gate controls who may read a memory entry, not whether its content is true. An operator who approves a cross-channel read admits whatever an attacker wrote there earlier. |
| T2 Tool Misuse | "Tool Misuse occurs when attackers manipulate AI agents to abuse their integrated tools through deceptive prompts or commands, operating within authorized permissions. This includes Agent Hijacking, where an AI agent ingests adversarial manipulated data and subsequently executes unintended actions, potentially triggering malicious tool interactions." | Pre-execution validation on every call: the tier classifier resolves a shell command to its canonical verb, and any shell metacharacter forces a sentinel that cannot match the Tier 2 allowlist, so an authorized verb cannot launder an unauthorized one downstream of the gate. Tool calls are capped at 20 rounds per turn, and every call is written to the chain before it runs. [permissions-and-identity.md](permissions-and-identity.md) | Workspace TOCTOU: files inside the workspace may be modified by any process at the same UID between the agent's read and its use of the contents. The cap-std confinement defends against the agent escaping the workspace, not against same-UID writers racing it inside. |
| T3 Privilege Compromise | "Privilege Compromise arises when attackers exploit weaknesses in permission management to perform unauthorized actions. This often involves dynamic role inheritance or misconfigurations." | On the inheritance half: the gate takes the session id and the logical agent id separately, so a child agent is checked against its own configured identity and inherits none of its parent's persisted grants. On the misconfiguration half: only Tier 2 keys are storable, and a grant for a Tier 1 or Tier 3 key is refused at write time rather than stored inert. [permissions-and-identity.md](permissions-and-identity.md) | Tier 2 approvals are per permissions-store, not per operator: everyone driving the same data dir inherits the others' approvals. |
| T4 Resource Overload | "Resource Overload targets the computational, memory, and service capacities of AI systems to degrade performance or cause failures, exploiting their resource-intensive nature." | Quotas at every layer: 20 tool rounds per turn, a separate per-child round budget, a 300s exec timeout, 512 MB and 256 PIDs per container, per-agent spend ceilings, auth limiting at 5 failures per 60s with no loopback exemption, and Cap'n Proto traversal limits that bound deserialization work on a malformed frame. [enforcement-model.md](enforcement-model.md#rate-limits), [cost-monitoring.md](cost-monitoring.md) | None beyond the local-attacker floor. |
| T6 Intent Breaking & Goal Manipulation | "This threat exploits vulnerabilities in an AI agent's planning and goal-setting capabilities, allowing attackers to manipulate or redirect the agent's objectives and reasoning. One common approach is Agent Hijacking mentioned in Tool Misuse." | Phase overlays are boundary management for a skill's own pass structure: a skill declares a deny set across tools, egress hosts, read paths, write paths and inference providers for the remainder of a phase, and the gate refuses a denied call with a typed `Phase` reason even when a later LLM step asks for it. [skills.md](skills.md#phase-boundaries) | Overlays apply only where a skill declares them, and a skill cannot read overlay state. Nothing validates the agent's plan itself, and redirection that stays inside the declared set is not detected. |
| T8 Repudiation & Untraceability | "Occurs when actions performed by AI agents cannot be traced back or accounted for due to insufficient logging or transparency in decision-making processes." | Every action is a typed event written before it executes, in a per-session SHA-256 chain with Ed25519-signed chain heads, replayable offline against recorded message and tool hashes, forwarded to a SIEM in real time. [audit-cli.md](audit-cli.md), [siem-forwarder.md](siem-forwarder.md) | The signing key is held by the process that writes the chain, so the signature is meaningful for offline replay and third-party detection, not as a guarantee of fidelity at write time. Tamper-evidence against a same-UID attacker needs an anchor held off the machine. |
| T9 Identity Spoofing & Impersonation | "Attackers exploit authentication mechanisms to impersonate AI agents or users to perform unauthorized actions under false identities. This includes the theft or misuse of a formal, persistent agent identity (e.g., Microsoft Entra Agent ID), enabling privileged, long-term API access that bypasses the agent's conversational interface and its guardrails." | Each adapter authenticates with a per-adapter Ed25519 challenge-response whose signature covers `(domain \|\| adapter_id \|\| nonce)`, binding the identity cryptographically rather than through a pubkey lookup alone. After handshake the gateway pins the adapter's channel and rejects any frame declaring another. Credentials never reach the model, so a hijacked agent cannot read the material that represents it. [enforcement-model.md](enforcement-model.md#adapter-authentication-identity), [credentials.md](credentials.md) | The persistent-identity half is the weaker one: per-agent signing keys sit at `agents/<id>/identity.key` at the wirken UID, so a same-UID attacker can sign as that agent. Nothing detects impersonation behaviourally. |
| T11 Unexpected RCE and Code Attacks | "Attackers exploit AI-generated execution environments to inject malicious code, trigger unintended system behaviors, or execute unauthorized scripts." | `exec` runs in an ephemeral container with all capabilities dropped, `no-new-privileges`, a read-only root filesystem, no network by default and a non-root user; Wasm skills run under a fuel limit with no filesystem and no network. When the runtime is unavailable, `exec` is refused rather than run on the host. [sandbox-properties.md](sandbox-properties.md) | `sandbox.json` `mode: off` runs `exec` at the wirken UID with no container, and the host shell can then rewrite every trust file under the data dir. MCP children spawn at that UID with no process sandbox. |
| T13 Rogue Agents in Multi-Agent Systems | "Malicious or compromised AI agents operate outside normal monitoring boundaries, executing unauthorized actions or exfiltrating data, including the concept of \"infectious backdoors\" where one compromised agent spreads malicious logic to others" | There is no path for an agent to act outside the monitored boundary: every tool call routes through one gate and lands on the chain before execution, unregistered tool names default-deny, and org `blocked_tools` fails a name before dispatch. Spread is bounded by a hard sub-agent depth cap of 4. [multi-agent.md](multi-agent.md#sub-agent-orchestration) | OWASP notes cryptographic attestation of model integrity does not yet exist, and wirken has none either: nothing detects that an agent has drifted while its individual calls stay inside policy. |
| T14 Human Attacks on Multi-Agent Systems | "Adversaries exploit inter-agent delegation, trust relationships, and workflow dependencies to escalate privileges or manipulate AI-driven operations." | Delegation is restricted rather than trusted: the operator declares which children a parent may spawn and the ceiling for each, the harness intersects the LLM's requested tool set with that allowlist, clamps the tier, and caps rounds and runtime. The LLM cannot widen any of it, and a child gains nothing from its parent's grants. [multi-agent.md](multi-agent.md#sub-agent-orchestration) | Sub-agents run in the parent's process, so the boundary is the harness rather than an OS one. |
| T15 Human Manipulation | "In scenarios where AI agents engage in direct interaction with human users, the trust relationship reduces user skepticism, increasing reliance on the agent's responses and autonomy. This implicit trust and direct human/agent interaction create risks, as attackers can coerce agents to manipulate users, spread misinformation, and take covert actions." | Responses are stripped of ANSI and C1 control sequences at the print boundary, so a hostile skill cannot have the model render a convincing fake prompt such as a password request in the operator's terminal. The raw response stays on the chain unchanged, since the audit write is upstream of the print. Inbound messages are scanned for system-prompt extraction and instruction overrides and flagged on the row. [skills.md](skills.md) | Covers the terminal rendering path only. Nothing validates the content of what the agent tells a user, and injection detection flags rather than blocks. |
| T16 Insecure Inter-Agent Protocol Abuse | "Attacks target flaws in protocols like MCP or A2A, such as consent bypass or context hijacking, leading to unauthorized agent actions." | On consent bypass: every MCP tool call is Tier 3 and prompts on each use, and `mcp.json` entries can carry an Ed25519 signature over a canonical hash of the entry, refused at spawn under an anchored build. MCP servers run in a separate proxy process with a sanitised environment, and the agent never sees their credentials. [mcp.md](mcp.md), [signing.md](signing.md) | The signature attests the entry config, not the binary at `command`. A spawned server is unsandboxed and unconstrained once running, and the entry gate has a documented bypass. |
| T17 Supply Chain Compromise | "A compromised supply chain can result in vulnerable, malicious, outdated, or otherwise harmful components being included into the agent, allowing an attacker to manipulate agent actions, obtain data, or run arbitrary code. This can occur via models, libraries, tools, poisoned build environments, or other system components." | Artifacts are digitally signed at each layer: skill bundles verified at install and again at every load against a registry-anchored key with optional operator root delegation, MCP entries signed over a canonical hash, release binaries carrying signed checksums plus SLSA Build L3 provenance from the build workflow. Every Ed25519 verification uses `verify_strict`, rejecting non-canonical encodings and small-order points. Dependency advisories gate a release with `unsound` and `yanked` enforced. [signing.md](signing.md), [release-process.md](release-process.md) | No SBOM or AIBOM is produced. Default builds ship an empty compile-time registry anchor, so the registry-provided key is the sole anchor unless an operator sets a root, and rotating a compile-time anchor requires rebuilding the binary. Model weights are not attested. |

## OWASP Top 10 for Agentic Applications (2026)

Risk text is quoted verbatim from
[OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/),
December 2025. It is a separate list from T1-T17 above and cross-references
it. Citations name a `fn`, `const` or type; the line number is a hint that
drifts, so grep the symbol. Ratings: `Mitigated` (addressed on the live
dispatch path), `Partial` (addressed with a documented gap or operator
opt-out), `Partial (detection only)` (observed and logged, not blocked).

| ASI | OWASP definition | Control | Rating | Gap or opt-out |
|-----|------------------|---------|--------|----------------|
| ASI01 Agent Goal Hijack | "attackers can manipulate an agent's objectives, task selection, or decision pathways through a variety of techniques - including, but not limited to, prompt-based manipulation, deceptive tool outputs, malicious artefacts, forged agent-to-agent messages, or poisoned external data" | `InjectionDetector::scan` (`crates/gateway/src/injection_detect.rs:105`) from `message_loop` (`crates/cli/src/commands/run.rs:3164`); the `exec` tier gate (`tool_to_action`, `crates/agent/src/tool.rs:1721`; `Action::tier`, `crates/gateway/src/permissions.rs:224`); per-skill phase overlays | Partial (detection only) | Detection tags the row and emits `message.threat_flagged` (`run.rs:3191`) but does not block or downgrade. A hijacked goal is bounded by the downstream tool gate, not prevented at the prompt. The deceptive-tool-output vector is unaddressed: tool results enter the conversation without validation. |
| ASI02 Tool Misuse and Exploitation | "This entry covers cases where the agent operates within its authorized privileges but applies a legitimate tool in an unsafe or unintended way" | `tool_to_action` (`tool.rs:1721`) with `TIER2_ALLOWLIST` (`permissions.rs:195`) and the `SHELL_METACHARS` pipeline sentinel (`tool.rs:1624`, applied at `:1730`), which is precisely the within-privileges case: an allowlisted verb carrying a metacharacter resolves to a sentinel that cannot match the allowlist. MCP tools at Tier 3; unregistered names default-deny via `Action::UnknownTool` (`runtime.rs:3036`); org allow and deny lists (`runtime.rs:2980`); veto hooks | Partial | The skill-set allowlist covers `web_search`, `generate_image`, `http_request` and the Zirkel transport (`EgressClient`, `egress.rs:167`); MCP children and the LLM client are unmediated. `exec` is bounded on a separate per-channel axis defaulting to no networking. `sandbox.json mode: off` runs `exec` on the host. |
| ASI03 Identity and Privilege Abuse | "exploits dynamic trust and delegation in agents to escalate access and bypass controls by manipulating delegation chains, role inheritance, control flows, and agent context... Agent-to-agent trust or inherited credentials can be exploited to escalate access" | The delegation-chain case is the load-bearing one and is closed structurally: `PermissionStore::check` (`permissions.rs:729`) takes the session id and the logical agent id as separate arguments, so a child is checked against its own identity and inherits no persisted grant from its parent. Around it, the tier clamp `set_subagent_runtime` (`runtime.rs:1525`), depth cap `MAX_SUBAGENT_DEPTH` = 4 (`runtime.rs:60`) and tool-allowlist intersection (`bind_as_subagent`, `runtime.rs:1560`) | Partial | A Tier 2 approval is per permissions-store, not per user: one sender's approval applies to every sender on a shared agent until it expires. |
| ASI04 Agentic Supply Chain Vulnerabilities | "arise when agents, tools, and related artefacts they work with are provided by third parties and may be malicious, compromised, or tampered with in transit... including models and model weights, tools, plug-ins, datasets, other agents, agentic interfaces - MCP (Model Context Protocol), A2A (Agent2Agent) - agentic registries and related artifacts, or update channels" | `verify_skill_signature` (`crates/agent/src/skill.rs:510`) against a registry-anchored key with optional root delegation (`skill_registry.rs:398`), the same check gating install (`skills.rs:64`); MCP entry signatures; signed release binaries with SLSA provenance | Partial | Opt-outs `WIRKEN_ALLOW_UNSIGNED_SKILLS` (`skill.rs:18`), `_MCP`, `_ORG_CONFIG`. Of the artefact classes OWASP names, model weights and datasets are unattested; the registry and update channel are covered. MCP children spawn at the wirken UID with no sandbox. |
| ASI05 Unexpected Code Execution (RCE) | "Attackers exploit code-generation features or embedded tool access to escalate actions into remote code execution (RCE), local misuse, or exploitation of internal systems... ASI05 focuses on unexpected or adversarial execution of code (scripts, binaries, JIT/WASM modules, deserialized" | `exec` in a Docker or gVisor sandbox (`ToolExecutor::sandbox`, `tool.rs:565`) with `cap_drop=ALL`, `no-new-privileges`, read-only rootfs and no network by default (`build_host_config`, `sandbox.rs:994`); refusal rather than host fallback (`tool.rs:708-733`); the WASM-module case covered by a fuel limit and no filesystem or network (`wasm_sandbox.rs:64`, `:125`); 300s timeout (`sandbox.rs:265`, enforced `:457`); exec tiering classifies on the resolved symlink target, not the lexical basename | Mitigated (with opt-out) | `sandbox.json mode: off` runs `exec` on the host at the wirken UID; the gateway warns at startup. |
| ASI06 Memory & Context Poisoning | "adversaries corrupt or seed this context with malicious or misleading data, causing future reasoning, planning, or tool use to become biased, unsafe, or aid exfiltration. Ingestion sources such as uploads, API feeds, user input, or peer-age" | Retained context is the append-only chain replayed on wake (`SessionLog::append` / `verify`, `session_log.rs:1996`, `:2050`), so a modified turn breaks it. Ingestion is gated: `CrossChannelMemoryRead`, `ImportedChatRead` and `ImportedChatSearch` are Tier 3 (`permissions.rs:224`) and none can be pre-approved by key, and memory entries carry runtime-stamped provenance labels no tool argument can set | Partial | Tier 3 controls disclosure, not the integrity of what is disclosed: approving a cross-channel read admits whatever an attacker wrote there earlier. Summaries and compaction output re-enter the prompt unvalidated. The workspace is writable by any process at the wirken UID between an agent's read and its use of the bytes. |
| ASI07 Insecure Inter-Agent Communication | "Weak inter-agent controls for authentication, integrity, confidentiality, or authorization let attackers intercept, manipulate, spoof, or block messages... Insecure Inter-Agent Communication occurs when these exchanges lack proper authentication, integrity, or semantic validation" | Structural rather than defensive: there is no inter-agent transport to attack. Sub-agents are invoked in-process and return a JSON result envelope, with no message bus, no shared mutable memory between agents and no network hop. The one cross-process link, adapter to gateway, carries an Ed25519 handshake (`perform_gateway_handshake`, `crates/ipc/src/auth.rs:178`), a 16 MB frame bound and 64-level nesting limit (`MAX_FRAME_SIZE`, `transport.rs:7`), and per-frame channel-mismatch rejection (`run.rs:3119`) | Mitigated | Mitigated by absence, not by a control: an inter-agent protocol added later would need its own authentication and semantic validation, and the in-process envelope is not semantically validated today. The IPC sockets are a same-user trust boundary. |
| ASI08 Cascading Failures | "a single fault (hallucination, malicious input, corrupted tool, or poisoned memory) propagates across autonomous agents, compounding into system-wide harm... a single error can bypass stepwise human checks and persist in a saved state" | Propagation is bounded by `MAX_TOOL_ROUNDS` = 20 (`runtime.rs:25`), `MAX_SUBAGENT_DEPTH` = 4 (`runtime.rs:60`), per-child round and runtime budgets, the 300s exec timeout, and rate limiters with no loopback exemption (`rate_limit.rs:11`, `:132`). On the saved-state half, an incomplete tool round is detected on wake and surfaced as a failure rather than silently re-executed | Partial | Downgraded from Mitigated against the definition's saved-state clause: a poisoned memory entry persists across turns and nothing validates its content on replay, so a fault seeded in long-term memory is not bounded by any of the caps above. |
| ASI09 Human-Agent Trust Exploitation | "Adversaries or misaligned designs may exploit this trust to influence user decisions, extract sensitive information, or steer outcomes... amplified when humans over-rely on autonomous recommendations or unverifiable rationales, approving actions without independent validation" | Tier 3 always prompts and is served from neither grant store: `check` gates the session-cache short-circuit on tier (`permissions.rs:750`) and answers Tier 3 without consulting storage (`:807`), and both `approve_by_key` and the session-scoped write refuse a non-Tier-2 key, so the property holds by structure at both the read and the write side. The prompt carries the tool, tier and the triggering message, so the operator has material to validate against rather than the agent's own rationale; responses are stripped of ANSI and C1 control sequences at the print boundary so a hostile skill cannot render a convincing fake prompt | Partial | Prompting on every Tier 3 use is itself an approval-fatigue surface, which is the over-reliance the definition describes. Nothing here validates the agent's rationale, only what it is asking to run. |
| ASI10 Rogue Agents | "malicious or compromised AI Agents that deviate from their intended function or authorized scope... The agent's actions may individually appear legitimate, but its emergent behavior becomes harmful... ASI10 focuses on the loss of behavioral integrity and governance once the drift begins" | Per-agent Ed25519 identity and session attestation (`attestation.rs:86`, `:134`); tamper-evident chain (`session_log.rs:2050`); org `blocked_tools` as a configuration-time kill switch (`runtime.rs:2980`); unregistered tools default-deny (`runtime.rs:3036`); sub-agent ceilings | Partial | The definition's centre is unaddressed: nothing detects emergent drift whose individual actions each pass the gate. The chain records what happened for after-the-fact review; it does not judge behaviour. Revocation requires a config push and a gateway restart, and there is no central registry across instances. |

## Documented escape hatches

The defaults above are deliberately strict. Each knob below is opt-in, emits a
`tracing::warn!` every time it engages, and leaves the operator on the hook for
what the relaxed posture loses. A one-shot env var on the command line is not
durable across reboots, so the practical forms are a systemd
`EnvironmentFile`, a shell `rc` export, or a wrapper script that invokes
`wirken run`.

| Knob | What it disables |
|------|------------------|
| `WIRKEN_ALLOW_UNSIGNED_ORG_CONFIG=1` | Ed25519 verification of the org-config bundle pulled from the policy URL. The bundle is then trusted on HTTPS and URL pinning alone. The gateway logs a warn on every fetch. |
| `WIRKEN_ALLOW_UNSIGNED_SKILLS=1` | Both skill gates. At install, lands a registry skill that has no `signer_key` in the index entry. At load, accepts a bundle with no `SKILL.sig` / `SKILL.pub`. Neither gate accepts a present-but-invalid signature, and neither bypass applies once a registry root is configured. See [signing](signing.md#skill-signing). |
| `WIRKEN_ALLOW_UNSIGNED_MCP=1` | Lets the MCP proxy spawn an `mcp.json` entry carrying no `signature` even under a build compiled with a populated anchor. Invalid signatures are never bypassed. Each spawn lands an `mcp_entry_verified` row with signer `<unsigned-bypass>` on the `gateway-mcp` sentinel session. |
| `WIRKEN_ALLOW_STALE_ORG_CONFIG=1` | The org-config freshness window, including a `signed_at` in the future, which usually means clock skew or replay. The signature itself is still verified. Each bypass warns with the bundle's age and the configured `max_age_seconds`. |
| `WIRKEN_WEBCHAT_ALLOW_NO_ORIGIN=1` | The `Origin` header check on the webchat `/api/chat` endpoint. Same-host non-browser callers can drive the agent; same-UID becomes the sole trust boundary. Warn at startup. |
| `WIRKEN_ALLOW_UNREGISTERED_HOOKS=1` | Flips the veto- and egress-hook timeout path from fail-closed to fail-open, and admits a hook process whose id is not in the registry. A hook that times out then passes the tool call through instead of refusing it. The audit row records the timeout either way. See [enforcement model](enforcement-model.md#veto-and-egress-hooks). |
| `WIRKEN_AUDIT_VERIFY_EVERY_FLUSHES=N` | Sets the flush cycles between continuous chain-verification passes (default 100). Above 10,000 the in-process verifier is effectively disabled, so a chain break is caught only at the next operator-run `wirken audit verify`. Only the above-10,000 case warns; smaller departures do not. |
| `sandbox.json` `mode: off` | Runs `exec` directly on the host at the wirken UID instead of inside a container. The only remaining gate is the permission tier, and the host shell can read or rewrite every trust file under the data dir (`tool_policy.json`, `sandbox.json`, `org.url`, `org-config-pubkey.pub`, `audit.db`, `vault.db`, `agents/<id>/identity.key`, `audit-alarms.log`); changes take effect at the next gateway start. Edit the file once; persists across restarts; gateway warns at startup. |
| `WIRKEN_ALLOW_UNVERIFIED=1` *(install-time only)* | The release-binary checksum and signature verification step in `install.sh`. The binary is installed on the strength of the network and the URL alone. Not honored at runtime; re-running `install.sh` is the only way to engage it. |

## NIST AI Risk Management Framework

Subcategory text is quoted verbatim from
[NIST AI 100-1](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.100-1.pdf),
Tables 1 to 4. Only subcategories whose text a shipped mechanism actually
satisfies are listed; most of the framework addresses organizational process
that a tool cannot discharge, and those are absent rather than mapped to
something adjacent.

A row is a claim about the mechanism, not a claim that an adopting
organization satisfies the subcategory. Four of the MEASURE entries below
qualify their scope with "as identified in the MAP function"; wirken does not
perform an organization's MAP function, so that qualifier stays the adopter's
to satisfy.

| Subcategory | Verbatim text | Mechanism | What it does not cover |
|---|---|---|---|
| GOVERN 1.7 | "Processes and procedures are in place for decommissioning and phasing out AI systems safely and in a manner that does not increase risks or decrease the organization's trustworthiness." | An ordered uninstall procedure that exports the audit chain before anything is destroyed, removes the service and scheduled entries before the binary they depend on, and enumerates the platform-side registrations and tokens that local deletion does not touch. [README](../README.md#uninstall), [channels.md](channels.md#platform-side-state) | Nothing automates it; the operator runs the steps. |
| MAP 4.2 | "Internal risk controls for components of the AI system, including third-party AI technologies, are identified and documented." | Signature verification on third-party skill bundles and `mcp.json` entries, applied at install and again at every load, with an optional operator registry root. [signing.md](signing.md) | Both gates have a documented opt-out, and MCP server children run at the wirken UID with no process sandbox once spawned. |
| MEASURE 2.4 | "The functionality and behavior of the AI system and its components – as identified in the MAP function – are monitored when in production." | Every tool call, gate decision, model call and refusal is written as a typed event before it executes, and forwarded in real time to Datadog, Splunk HEC, Microsoft Sentinel or a webhook. [audit-cli.md](audit-cli.md), [siem-forwarder.md](siem-forwarder.md) | Forwarding is best-effort with no retry; the local chain is the durable record. |
| MEASURE 2.6 | "The AI system is evaluated regularly for safety risks – as identified in the MAP function. The AI system to be deployed is demonstrated to be safe, its residual negative risk does not exceed the risk tolerance, and it can fail safely, particularly if made to operate beyond its knowledge limits. Safety metrics reflect system reliability and robustness, real-time monitoring, and response times for AI system failures." | The "fail safely" clause, on the dispatch path. `exec` is refused rather than run on the host when the sandbox is unavailable; an unregistered tool name resolves to Tier 3; a present-but-unparseable registry root refuses every skill; a ledger error under a block-mode budget refuses the call; a sidecar that cannot start refuses the `exec`. [sandbox-properties.md](sandbox-properties.md#no-silent-fallback), [permissions-and-identity.md](permissions-and-identity.md) | The rest of the subcategory. There is no regular safety evaluation, no residual-risk determination against a stated tolerance, and no safety metrics for reliability or failure response times. |
| MEASURE 2.7 | "AI system security and resilience – as identified in the MAP function – are evaluated and documented." | This document and [sandbox-properties.md](sandbox-properties.md), which pair each control with its gap and cite the symbol that implements it, plus the verification commands an operator can run to confirm the sandbox behaves as described. | Evaluation is by the maintainers against the code. No third party has assessed it. |
| MEASURE 2.8 | "Risks associated with transparency and accountability – as identified in the MAP function – are examined and documented." | A per-session hash chain with per-agent attestation, plus the documented limits of what it proves: that the signing key is held by the process that writes the chain, and that the default anchor is co-resident, so verification emits a warning naming what it does not establish. [audit-cli.md](audit-cli.md) | Tamper-evidence against a same-UID attacker needs an anchor held off the machine, which is the operator's to arrange. |
| MANAGE 2.4 | "Mechanisms are in place and applied, and responsibilities are assigned and understood, to supersede, disengage, or deactivate AI systems that demonstrate performance or outcomes inconsistent with intended use." | Org policy `blocked_tools` fails a named tool before dispatch; `wirken permissions revoke` drops a grant with immediate effect; `wirken sessions close` ends a session; `wirken preset unschedule` stops a scheduled agent. The operator is the approver, and every denial is recorded with the surface it came from. [enterprise.md](enterprise.md), [permissions-and-identity.md](permissions-and-identity.md) | Org-policy changes take effect at the next gateway start, so deactivation through that path is not immediate. There is no central registry or live revocation across instances. |

Subcategories wirken ships no mechanism for, including the whole of the
GOVERN function beyond 1.7, are deliberately absent.
