# Security properties

Four mapping tables, the model's context, the exec perimeter, and the escape-hatch inventory. Every mechanism named
here is owned by another page; the cells say what the control is and link to
where it is described, rather than restating it.

- Permission tiers, approvals, identity: [permissions-and-identity.md](permissions-and-identity.md)
- Audit chain, events, verification: [audit-cli.md](audit-cli.md)
- Sandbox: [sandbox-properties.md](sandbox-properties.md)
- Egress, both axes: [egress.md](egress.md)
- Signing surfaces: [signing.md](signing.md)
- Compile-time vs runtime enforcement: [enforcement-model.md](enforcement-model.md)

Every rating sits on the same floor: a process running at the wirken UID is
outside the model.

Wirken makes no claim about tracking data through the model and gates the
action edge instead.

## OWASP Agentic AI Threats and Mitigations

Threat text is quoted verbatim from
[Agentic AI - Threats and Mitigations](https://genai.owasp.org/resource/agentic-ai-threats-and-mitigations/),
v1.1, December 2025, which numbers its threats T1 to T17. A row is here only
where a shipped mechanism addresses the threat as that text defines it;
T5, T6, T7, T10, T12 and T15 have no wirken control that does what their text describes and are absent.

| TID | OWASP definition | Mechanism | Gap |
|-----|------------------|-----------|-----|
| T1 Memory Poisoning | "Memory Poisoning involves exploiting an AI's memory systems, both short and long-term, to introduce malicious or false data and exploit the agent's context. This can lead to altered decision-making and unauthorized operations." | Short-term memory is the per-session hash chain, replayed on wake, so a modified turn breaks its own chain. Long-term memory entries carry five origin labels stamped by the runtime from the turn's inbound context and unreachable from tool arguments, so a model cannot author its own provenance; a turn missing any of them writes no entry at all. Reading another channel's entries is Tier 3 and cannot be pre-approved. [enforcement-model.md](enforcement-model.md#cross-channel-memory), [audit-cli.md](audit-cli.md) | Provenance is recorded, not validated: the gate controls who may read a memory entry, not whether its content is true. An operator who approves a cross-channel read admits whatever an attacker wrote there earlier. |
| T2 Tool Misuse | "Tool Misuse occurs when attackers manipulate AI agents to abuse their integrated tools through deceptive prompts or commands, operating within authorized permissions. This includes Agent Hijacking, where an AI agent ingests adversarial manipulated data and subsequently executes unintended actions, potentially triggering malicious tool interactions." | Pre-execution validation on every call: the tier classifier resolves a shell command to its canonical verb, and any shell metacharacter forces a sentinel that cannot match the Tier 2 allowlist, so an authorized verb cannot launder an unauthorized one downstream of the gate. Tool calls are capped at 20 rounds per turn (60 for each agent of Lyrik's fix step, or the operator's `fix_tool_rounds`), and every call is written to the chain before it runs. A reply the provider ends as a refusal is not acted on: none of its tool calls is dispatched, and the last call of a reply cut off at the output token limit is not dispatched either. Each such call gets a `withheld` result on the chain that names the mapped stop reason and the provider's own word, the model is given the same result, and because this happens ahead of the permission gate no approval is asked for it. Exact-match leak detection on the stored secrets: a tool call whose arguments carry one is recorded with the refusal in their place and does not run; a tool's output, the request to the model, the reply, a user's message and a skill carrying one are refused before they go further; each refusal is a `leak_refused` row naming the credential ([architecture.md](architecture.md#2-credential-lifecycle)). [permissions-and-identity.md](permissions-and-identity.md) | Leak detection matches exact raw bytes of secrets the vault holds: an encoded form (base64, URL or JSON escaping), a secret split across two pieces of content, a secret under 8 bytes, and a secret the vault does not hold all pass, the identity, audit and operator key files excepted; there is no pattern list. Withholding on refusal rests on the provider reporting one: Anthropic (`refusal`), OpenAI-compatible endpoints including Tinfoil (`content_filter`), Gemini (`SAFETY`, `RECITATION`, `BLOCKLIST`, `PROHIBITED_CONTENT`, `SPII`) and Bedrock (`content_filtered`, `guardrail_intervened`) do; Ollama reports only `stop` and `length`, and the subscription-plan path does not pass a stop reason through, so on those a refusal is not seen and nothing is withheld for it. Workspace TOCTOU: files inside the workspace may be modified by any process at the same UID between the agent's read and its use of the contents. The cap-std confinement defends against the agent escaping the workspace, not against same-UID writers racing it inside. |
| T3 Privilege Compromise | "Privilege Compromise arises when attackers exploit weaknesses in permission management to perform unauthorized actions. This often involves dynamic role inheritance or misconfigurations." | On the inheritance half: the gate takes the session id and the logical agent id separately, so a child agent is checked against its own configured identity and inherits none of its parent's persisted grants. On the misconfiguration half: only Tier 2 keys are storable, and a grant for a Tier 1 or Tier 3 key is refused at write time rather than stored inert. [permissions-and-identity.md](permissions-and-identity.md) | A Tier 2 grant is per agent and channel, not per sender: every admitted sender on that agent and channel is covered by it. |
| T4 Resource Overload | "Resource Overload targets the computational, memory, and service capacities of AI systems to degrade performance or cause failures, exploiting their resource-intensive nature." | Quotas at every layer: 20 tool rounds per turn (60 for each agent of Lyrik's fix step, or the operator's `fix_tool_rounds`), a separate per-child round budget, a 300s exec timeout, 512 MB and 256 PIDs per container unless the data directory's `sandbox.json` sets other limits, a per-agent spend ceiling where a budget is configured, a WebChat request limit (`ControlPlaneRateLimiter`), Cap'n Proto traversal limits that bound deserialization work on a malformed frame, and on the proxy listener per-token call and spend ceilings, a request body limit and an idle timeout. [enforcement-model.md](enforcement-model.md#rate-limits), [cost-monitoring.md](cost-monitoring.md), [inference-proxy.md](inference-proxy.md#limits-per-token) | No authentication path is rate limited, the proxy's token check included. A proxy token issued without a ceiling is unbounded, and a ceiling counts model calls, not tool calls ([threat-model.md](threat-model.md#proxy-clients)). |
| T8 Repudiation & Untraceability | "Occurs when actions performed by AI agents cannot be traced back or accounted for due to insufficient logging or transparency in decision-making processes." | Every tool call is a typed event written before it executes, and its outcome a typed event written after, in a per-session SHA-256 chain with Ed25519-signed chain heads, checkable offline against recorded message and tool hashes, and forwarded to a SIEM by a polling forwarder where one is configured. A model call forwarded for a proxy client is a request row before it is sent and a response row after, each with the SHA-256 of its body; a proxy client's tool call is recorded as an agent's is. [audit-cli.md](audit-cli.md), [siem-forwarder.md](siem-forwarder.md), [proxy.md](proxy.md#what-is-recorded) | Stated in [threat-model.md](threat-model.md#audit). |
| T9 Identity Spoofing & Impersonation | "Attackers exploit authentication mechanisms to impersonate AI agents or users to perform unauthorized actions under false identities. This includes the theft or misuse of a formal, persistent agent identity (e.g., Microsoft Entra Agent ID), enabling privileged, long-term API access that bypasses the agent's conversational interface and its guardrails." | Each adapter authenticates with a per-adapter Ed25519 challenge-response whose signature covers `(domain \|\| adapter_id \|\| nonce)`, binding the identity cryptographically rather than through a pubkey lookup alone. After handshake the gateway pins the adapter's channel and rejects any frame declaring another. Credentials never reach the model, so a hijacked agent cannot read the material that represents it. A proxy client authenticates with a Wirken-issued token stored only as a SHA-256 digest, limited to named upstreams, models and MCP servers and to its ceilings, and refused from the request after its revocation. [enforcement-model.md](enforcement-model.md#adapter-authentication-identity), [credentials.md](credentials.md), [inference-proxy.md](inference-proxy.md#tokens) | A proxy token is a bearer secret with no expiry and no binding to a client address: whoever holds it is that client until it is revoked. The persistent-identity half is the weaker one: per-agent signing keys sit at `agents/<id>/identity.key` at the wirken UID, so a same-UID attacker can sign as that agent. Nothing detects impersonation behaviourally. |
| T11 Unexpected RCE and Code Attacks | "Attackers exploit AI-generated execution environments to inject malicious code, trigger unintended system behaviors, or execute unauthorized scripts." | `exec` runs in an ephemeral container with all capabilities dropped, `no-new-privileges`, a read-only root filesystem, no network by default and a non-root user. When the runtime is unavailable, `exec` is refused rather than run on the host. [sandbox-properties.md](sandbox-properties.md) | `sandbox.json` `mode: off` runs `exec` at the wirken UID with no container, and the host shell can then rewrite every trust file under the data dir. A stdio MCP server whose entry sets `"sandbox": "off"` runs at that UID with no process sandbox; one with a `sandbox` block runs in its own container. |
| T13 Rogue Agents in Multi-Agent Systems | "Malicious or compromised AI agents operate outside normal monitoring boundaries, executing unauthorized actions or exfiltrating data, including the concept of \"infectious backdoors\" where one compromised agent spreads malicious logic to others" | A tool call of one of Wirken's own agents has no path outside the monitored boundary: every tool call routes through one gate and lands on the chain before execution, unregistered tool names default-deny, and org `blocked_tools` fails a name before dispatch. Spread is bounded by a hard sub-agent depth cap of 4. A client of the proxy is not such an agent: its model calls and its calls at the MCP endpoint are recorded and gated, its own tools are not. [multi-agent.md](multi-agent.md#sub-agent-orchestration), [proxy.md](proxy.md) | OWASP notes cryptographic attestation of model integrity does not yet exist, and wirken has none either: nothing detects that an agent has drifted while its individual calls stay inside policy. |
| T14 Human Attacks on Multi-Agent Systems | "Adversaries exploit inter-agent delegation, trust relationships, and workflow dependencies to escalate privileges or manipulate AI-driven operations." | Delegation is restricted rather than trusted: the operator declares which children a parent may spawn and the ceiling for each, the harness intersects the LLM's requested tool set with that allowlist, clamps the tier, and caps rounds and runtime. The LLM cannot widen any of it, and a child gains nothing from its parent's grants. [multi-agent.md](multi-agent.md#sub-agent-orchestration) | Sub-agents run in the parent's process, so the boundary is the harness rather than an OS one. |
| T16 Insecure Inter-Agent Protocol Abuse | "Attacks target flaws in protocols like MCP or A2A, such as consent bypass or context hijacking, leading to unauthorized agent actions." | On consent bypass: every MCP tool call is Tier 3 and prompts on each use, and `mcp.json` entries can carry an Ed25519 signature over a canonical hash of the entry, refused at spawn under an anchored build. MCP servers are reached through a separate proxy process, and the agent never sees their credentials. Each stdio server runs in its own hardened container with no network unless its signed entry lists hosts, reached then only through a per-server egress proxy; an entry with no `sandbox` block is refused. An HTTP server's calls follow no redirect. A credential an entry's `inject` block names stays out of the server's container. A client of the proxy listener reaches an agent's signed MCP servers at `POST /mcp` only with a token granted them; the tools a session is shown are fixed, and each call is Tier 3 ([proxy-mcp.md](proxy-mcp.md)). [mcp.md](mcp.md), [signing.md](signing.md) | What a signature covers, the empty anchor of the released build and `"sandbox": "off"` are stated in [threat-model.md](threat-model.md#mcp-servers). The entry gate has a documented bypass. An MCP OAuth refresh token carries no destinations of its own: the gateway sends it only to the provider's compiled-in token endpoint. The refresh socket serves only credentials whose destinations were checked when the proxy was handed them, and rechecks them for each value it sends; a revoke reaches the proxy within seconds. |
| T17 Supply Chain Compromise | "A compromised supply chain can result in vulnerable, malicious, outdated, or otherwise harmful components being included into the agent, allowing an attacker to manipulate agent actions, obtain data, or run arbitrary code. This can occur via models, libraries, tools, poisoned build environments, or other system components." | Artifacts are digitally signed at each layer: skill bundles verified at install and again at every load against the registry root (the project root compiled in, or the operator's), MCP entries signed over a canonical hash, release binaries carrying signed checksums plus SLSA Build L3 provenance from the build workflow. Every Ed25519 verification uses `verify_strict`, rejecting non-canonical encodings and small-order points. Dependency advisories gate a release with `unsound` and `yanked` enforced. [signing.md](signing.md), [release-process.md](release-process.md) | No SBOM or AIBOM is produced. The project registry root is compiled in; replacing it takes an operator root (`wirken skills trust-root`) or a rebuild. Model weights are not attested. |

## OWASP Top 10 for Agentic Applications (2026)

Risk text is quoted verbatim from
[OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/),
December 2025. It is a separate list from T1-T17 above and cross-references
it. Citations name a `fn`, `const` or type; the line number is a hint that
drifts, so grep the symbol. Ratings: `Mitigated` (addressed on the live
dispatch path), `Partial` (addressed with a documented gap or operator
opt-out), `Partial (detection only)` (observed and logged, not blocked).

| ASI | OWASP definition | Control | Rating | Gap or opt-out |
|-----|------------------|---------|--------|----------------|
| ASI01 Agent Goal Hijack | "attackers can manipulate an agent's objectives, task selection, or decision pathways through a variety of techniques - including, but not limited to, prompt-based manipulation, deceptive tool outputs, malicious artefacts, forged agent-to-agent messages, or poisoned external data" | `InjectionDetector::scan` (`crates/gateway/src/injection_detect.rs`) from `message_loop` (`crates/cli/src/commands/run.rs`) through `scan_catching_panics` (`crates/cli/src/commands/inbound_scan.rs`); the `exec` tier gate (`tool_to_action`, `crates/agent/src/tool.rs`; `Action::tier`, `crates/gateway/src/permissions.rs`); per-skill phase overlays | Partial (detection only) | Detection tags the row and emits `message.threat_flagged` (`message_loop`) but does not block or downgrade. A hijacked goal is bounded by the downstream tool gate, not prevented at the prompt. The deceptive-tool-output vector is unaddressed: tool results enter the conversation after a match for stored secrets and any registered egress hook, and nothing else validates them. |
| ASI02 Tool Misuse and Exploitation | "This entry covers cases where the agent operates within its authorized privileges but applies a legitimate tool in an unsafe or unintended way" | `tool_to_action` (`crates/agent/src/tool.rs`) with `TIER2_ALLOWLIST` (`crates/gateway/src/permissions.rs`) and the `SHELL_METACHARS` pipeline sentinel (`crates/agent/src/tool.rs`, applied in `tool_to_action`), which is precisely the within-privileges case: an allowlisted verb carrying a metacharacter resolves to a sentinel that cannot match the allowlist. MCP tools at Tier 3; unregistered names default-deny via `Action::UnknownTool` (`Agent::execute_tool`, `crates/agent/src/runtime.rs`); org allow and deny lists (`Agent::execute_tool`); veto hooks. The agent's reply is not a tool call and goes only to the conversation it answers (`message_loop`, `crates/cli/src/commands/run.rs`); a send to another channel or DM exists only as an MCP connector tool, Tier 3 on every call whatever the session has read, and never stored (corpus lines `mcp-send-other-channel`, `mcp-send-dm`) | Partial | The skill-set allowlist covers `web_search`, `generate_image`, `http_request` and the Zirkel transport (`EgressClient`, `crates/agent/src/egress.rs`). A fresh install attaches the 16 bundled skills, each with `egress: mode: deny` and none allowing these tools, so `web_search`, `generate_image` and `http_request` are refused there. An agent with no skills attached declares no allow-set: `http_request` reaches no host, and `web_search` and `generate_image`, which take no host from the model, are unrestricted. The paths no egress policy bounds are stated in [threat-model.md](threat-model.md#network). |
| ASI03 Identity and Privilege Abuse | "exploits dynamic trust and delegation in agents to escalate access and bypass controls by manipulating delegation chains, role inheritance, control flows, and agent context... Agent-to-agent trust or inherited credentials can be exploited to escalate access" | The delegation-chain case is the load-bearing one and is closed structurally: `PermissionStore::check` (`crates/gateway/src/permissions.rs`) takes the session id and the logical agent id as separate arguments, so a child is checked against its own identity and inherits no persisted grant from its parent. Around it, the tier clamp `Agent::set_subagent_runtime` (`crates/agent/src/runtime.rs`), depth cap `MAX_SUBAGENT_DEPTH` = 4 (same file) and tool-allowlist intersection (computed in `Agent::spawn_subagent_intercept` and `Agent::fan_out_spawns`, applied by `Agent::bind_as_subagent`). Who may drive an agent is the inbound sender allowlist (`InboundGate::check`, `crates/gateway/src/sender_registry.rs`), fail-closed per channel, checked before a message reaches a session, and for the proxy's MCP endpoint a token that names one agent and signed MCP servers of it, each call Tier 3 under that agent's gate (`Agent::run_tool_for_client`) | Partial | A Tier 2 grant is per agent and channel, not per user: it covers every admitted sender on that agent and channel until it expires. The allowlist admits the sender id the platform reports; it does not authenticate the person behind it. |
| ASI04 Agentic Supply Chain Vulnerabilities | "arise when agents, tools, and related artefacts they work with are provided by third parties and may be malicious, compromised, or tampered with in transit... including models and model weights, tools, plug-ins, datasets, other agents, agentic interfaces - MCP (Model Context Protocol), A2A (Agent2Agent) - agentic registries and related artifacts, or update channels" | `verify_skill_signature` (`crates/agent/src/skill.rs`) against the registry root, the project's compiled in or the operator's, by delegation (`verify_skill_with_expected_key_and_delegation`, reached through `verify_skill_delegated`, `crates/gateway/src/skill_registry.rs`), the same check gating install (`install`, `crates/cli/src/commands/skills.rs`). The bundled set is itself an artefact provided to the operator, so it ships the signature the project produced offline rather than one minted on the host at install: each directory carries `SKILL.sig`, `SKILL.pub` and `SKILL.deleg` under the published project root ([skills.md](skills.md)). MCP entry signatures; signed release binaries with SLSA provenance | Partial | Opt-outs `WIRKEN_ALLOW_UNSIGNED_SKILLS` (`ALLOW_UNSIGNED_ENV`, `crates/agent/src/skill.rs`; only in a build without a compiled root), `_MCP`, `_ORG_CONFIG`. Of the artefact classes OWASP names, model weights and datasets are unattested; the registry, the bundled set and the update channel are covered. A registry root is singular, so trusting the project's root for the bundled set means trusting it for every skill; an operator running their own root re-signs the bundle. A stdio MCP server with `"sandbox": "off"` runs at the wirken UID with no sandbox, and a contained one runs whatever its image holds. |
| ASI05 Unexpected Code Execution (RCE) | "Attackers exploit code-generation features or embedded tool access to escalate actions into remote code execution (RCE), local misuse, or exploitation of internal systems... ASI05 focuses on unexpected or adversarial execution of code (scripts, binaries, JIT/WASM modules, deserialized" | `exec` in a Docker or gVisor sandbox (`ToolRegistry::sandbox`, `crates/agent/src/tool.rs`) with `cap_drop=ALL`, `no-new-privileges`, read-only rootfs and no network by default (`build_host_config`, `crates/agent/src/sandbox.rs`); refusal rather than host fallback (`ToolRegistry::execute`); Wirken loads no WASM module, so that case does not arise; 300s timeout (`SandboxConfig::default`, enforced in `DockerSandbox::run_container`, `crates/agent/src/sandbox.rs`); exec tiering classifies on the resolved symlink target, not the lexical basename | Mitigated (with opt-out) | `sandbox.json mode: off` runs `exec` on the host at the wirken UID; the gateway warns at startup. |
| ASI06 Memory & Context Poisoning | "adversaries corrupt or seed this context with malicious or misleading data, causing future reasoning, planning, or tool use to become biased, unsafe, or aid exfiltration. Ingestion sources such as uploads, API feeds, user input, or peer-age" | Retained context is the tamper-evident chain replayed on wake (`SessionLog::append` / `verify`, `crates/audit/src/session_log.rs`), so a modified turn breaks it. Ingestion is gated: `CrossChannelMemoryRead`, `ImportedChatRead` and `ImportedChatSearch` are Tier 3 (`Action::tier`, `crates/gateway/src/permissions.rs`) and none can be pre-approved by key, and memory entries carry runtime-stamped provenance labels no tool argument can set | Partial | Tier 3 controls disclosure, not the integrity of what is disclosed: approving a cross-channel read admits whatever an attacker wrote there earlier. Summaries and compaction output re-enter the prompt unvalidated. The workspace is writable by any process at the wirken UID between an agent's read and its use of the bytes. |
| ASI07 Insecure Inter-Agent Communication | "Weak inter-agent controls for authentication, integrity, confidentiality, or authorization let attackers intercept, manipulate, spoof, or block messages... Insecure Inter-Agent Communication occurs when these exchanges lack proper authentication, integrity, or semantic validation" | Between Wirken's own agents there is no transport to attack: sub-agents are invoked in-process and return a JSON result envelope, with no message bus, no shared mutable memory between agents and no network hop. An agent Wirken does not run reaches tools over one link, the proxy listener's MCP endpoint (`POST /mcp`), authenticated by a proxy token and by TLS where `tls` is set, each call held to the tools its session was shown and to the agent's Tier 3 gate ([proxy-mcp.md](proxy-mcp.md)). The adapter to gateway link carries an Ed25519 handshake (`perform_gateway_handshake`, `crates/ipc/src/auth.rs`), a 16 MB frame bound and 64-level nesting limit (`MAX_FRAME_SIZE` and `read_message`, `crates/ipc/src/transport.rs`), and per-frame channel-mismatch rejection (`message_loop`, `crates/cli/src/commands/run.rs`) | Partial | The token is a bearer secret with no expiry, and on a bind without `tls` it crosses in the clear. Neither tool arguments on that link nor the in-process envelope are semantically validated. The IPC sockets are a same-user trust boundary. |
| ASI08 Cascading Failures | "a single fault (hallucination, malicious input, corrupted tool, or poisoned memory) propagates across autonomous agents, compounding into system-wide harm... a single error can bypass stepwise human checks and persist in a saved state" | Propagation is bounded by `MAX_TOOL_ROUNDS` = 20 and `MAX_SUBAGENT_DEPTH` = 4 (`crates/agent/src/runtime.rs`), per-child round and runtime budgets, the 300s exec timeout, and the WebChat request limit (`ControlPlaneRateLimiter`, `crates/gateway/src/rate_limit.rs`). No authentication path is rate limited. On the saved-state half, an incomplete tool round is detected on wake and surfaced as a failure rather than silently re-executed | Partial | Downgraded from Mitigated against the definition's saved-state clause: a poisoned memory entry persists across turns and nothing validates its content on replay, so a fault seeded in long-term memory is not bounded by any of the caps above. |
| ASI09 Human-Agent Trust Exploitation | "Adversaries or misaligned designs may exploit this trust to influence user decisions, extract sensitive information, or steer outcomes... amplified when humans over-rely on autonomous recommendations or unverifiable rationales, approving actions without independent validation" | Tier 3 always prompts and is served from neither grant store: `PermissionStore::check` (`crates/gateway/src/permissions.rs`) gates the session-cache short-circuit on tier and answers Tier 3 without consulting storage, and both `approve_by_key` and the session-scoped write refuse a non-Tier-2 key, so the property holds by structure at both the read and the write side. The prompt carries the tool, tier and the triggering message, so the operator has material to validate against rather than the agent's own rationale; responses are stripped of ANSI and C1 control sequences at the print boundary so a hostile skill cannot render a convincing fake prompt. Every value on the approval card (`crates/adapter-core/src/approval_card.rs`) is one line: escape sequences stripped, line breaks folded, a character that reorders or hides text written out as its code point, and a long value cut with a marker. Each channel escapes the value for its markup, and on Teams the label and the value are separate text runs that are not read as Markdown, so model text cannot draw a label, a link or a second line on the card. `tests/hostile/corpus.jsonl` replays this on every style. Each card shows the request id the gateway minted, a random UUID the model is never sent (`an_approval_id_is_random_and_never_reaches_the_model`, `crates/cli/src/commands/run.rs`), and a typed answer on Signal, iMessage or `wirken chat` carries its first four hex characters, so an answer binds to the card that showed the id and a card the model writes cannot name one | Partial | Prompting on every Tier 3 use is itself an approval-fatigue surface, which is the over-reliance the definition describes. Nothing here validates the agent's rationale, only what it is asking to run. |
| ASI10 Rogue Agents | "malicious or compromised AI Agents that deviate from their intended function or authorized scope... The agent's actions may individually appear legitimate, but its emergent behavior becomes harmful... ASI10 focuses on the loss of behavioral integrity and governance once the drift begins" | Per-agent Ed25519 identity and session attestation (`attest_session`, `verify_session_attestations`, `crates/agent/src/attestation.rs`); tamper-evident chain (`SessionLog::verify`, `crates/audit/src/session_log.rs`); org `blocked_tools` as a configuration-time kill switch (`Agent::execute_tool`, `crates/agent/src/runtime.rs`); unregistered tools default-deny (`Agent::execute_tool`); sub-agent ceilings | Partial | The definition's centre is unaddressed: nothing detects emergent drift whose individual actions each pass the gate. The chain records what happened for after-the-fact review; it does not judge behaviour. An agent is stopped at once with `wirken agents stop` and a proxy client with `wirken proxy token revoke`; an org `blocked_tools` change needs a gateway restart. There is no central registry across instances. |

## Proxy mode

What holds for a client Wirken does not run ([proxy.md](proxy.md)), each with
the test that shows it. What is outside these is in
[threat-model.md](threat-model.md#proxy-clients).

| Property | Test |
|---|---|
| The listener is off without a `proxy.json`, and binds beyond loopback only with `tls` or `bind_beyond_loopback` | `no_file_means_the_listener_is_off`, `a_bind_beyond_loopback_needs_its_own_setting` (`crates/gateway/src/proxy.rs`) |
| With `tls` the listener serves TLS and nothing else | `a_listener_with_a_certificate_serves_tls_and_nothing_else` (`crates/cli/src/commands/proxy_server.rs`) |
| A token is stored only as a digest and stops at its revocation | `a_token_is_valid_until_revoked_and_its_value_is_not_stored` (`crates/gateway/src/proxy.rs`) |
| A request with no valid token is refused with a row | `an_unknown_or_revoked_token_is_refused_with_a_row` (`proxy_server.rs`) |
| A token reaches only its models and stops at its ceilings | `a_tokens_model_list_and_ceilings_are_enforced`, `a_reached_spend_ceiling_refuses_the_call` (`proxy_server.rs`) |
| The provider key goes only where its vault entry allows, and no redirect is followed | `a_key_that_may_not_be_sent_refuses_the_call` (`proxy_server.rs`), `a_forwarded_request_follows_no_redirect` (`crates/agent/src/llm.rs`) |
| A forwarded request body is the client's, byte for byte: Wirken adds nothing to it | `a_request_is_forwarded_byte_for_byte_with_the_providers_key` (`crates/agent/src/llm.rs`), `a_chat_completion_is_forwarded_and_recorded_with_both_hashes` (`proxy_server.rs`) |
| A request carrying a stored secret is refused | `a_malformed_oversized_or_leaking_body_is_refused` (`proxy_server.rs`) |

| Claim | Shown by | Holds under | Does not hold under |

## Documented escape hatches

The defaults above are deliberately strict. Each knob below is opt-in, emits a
`tracing::warn!` every time it engages, and leaves the operator on the hook for
what the relaxed posture loses. A one-shot env var on the command line is not
durable across reboots, so the practical forms are a systemd
`EnvironmentFile`, a shell `rc` export, or a wrapper script that invokes
`wirken run`.

| Knob | What it disables |
|------|------------------|
| `WIRKEN_ALLOW_UNSIGNED_ORG_CONFIG=1` | Ed25519 verification of the org-config bundle pulled from the policy URL. The bundle is then trusted on HTTPS and URL pinning alone. The gateway logs a warn on every fetch. |
| `WIRKEN_ALLOW_UNSIGNED_SKILLS=1` | Only in a build without a compiled registry root. At install, lands a registry skill that has no `signer_key` in the index entry. At load, accepts a bundle with no `SKILL.sig` / `SKILL.pub`. Neither gate accepts a present-but-invalid signature. See [signing](signing.md#skill-signing). |
| `WIRKEN_ALLOW_UNSIGNED_MCP=1` | Lets the MCP proxy spawn an `mcp.json` entry carrying no `signature` even under a build compiled with a populated anchor. Invalid signatures are never bypassed. Each spawn lands an `mcp_entry_verified` row with signer `<unsigned-bypass>` on the `gateway-mcp` sentinel session. |
| `WIRKEN_ALLOW_STALE_ORG_CONFIG=1` | The org-config freshness window, including a `signed_at` in the future, which usually means clock skew or replay. The signature itself is still verified. Each bypass warns with the bundle's age and the configured `max_age_seconds`. |
| `WIRKEN_WEBCHAT_ALLOW_NO_ORIGIN=1` | The `Origin` header check on webchat's state-changing routes, for a request that sends no `Origin`. It relaxes that check only: every `/api` call still needs a login cookie or the session token as a bearer. Warn at startup. |
| `WIRKEN_ALLOW_UNREGISTERED_HOOKS=1` | Flips the veto- and egress-hook timeout path from fail-closed to fail-open, and admits a hook process whose id is not in the registry. A hook that times out then passes the tool call through instead of refusing it. The audit row records the timeout either way. See [enforcement model](enforcement-model.md#veto-and-egress-hooks). |
| `WIRKEN_AUDIT_VERIFY_EVERY_FLUSHES=N` | Sets the flush cycles between continuous chain-verification passes (default 100). Above 10,000 the in-process verifier is effectively disabled, so a chain break is caught only at the next operator-run `wirken audit verify`. Only the above-10,000 case warns; smaller departures do not. |
| `WIRKEN_LIVE_RELOAD_INTERVAL_S=N` | Sets the seconds between the gateway's looks at the vault, the adapter registry and the hook registry (default 2, at most 3600). A credential rotated or removed, an adapter removed or a hook unregistered by another process stays in force in the running gateway for up to that long. A value other than the default warns at startup; zero, a value above 3600, or one that is not a whole number stops `wirken run` before it starts. |
| `mcp.json` `"sandbox": "off"` on a stdio entry | Runs that one MCP server as a host process at the wirken UID instead of in a container: no capability drop, namespace, seccomp filter or resource limit, the operator's filesystem and network reach, and its `vault:` values in its environment. Part of the signed entry, so it cannot be set on a signed entry without re-signing. Each start warns and lands an `mcp_server_unsandboxed` row on the `gateway-mcp` session. |
| `proxy.json` `"bind_beyond_loopback": true` | Lets the proxy listener bind an address beyond loopback with no `tls`. Every client's token and every request and response then cross the network in the clear ([inference-proxy.md](inference-proxy.md#tls)). |
| `sandbox.json` `mode: off` | Runs `exec` directly on the host at the wirken UID instead of inside a container ([threat-model.md](threat-model.md#shell)). The only remaining gate is the permission tier, and the host shell can read or rewrite every trust file under the data dir (`tool_policy.json`, `sandbox.json`, `org.url`, `org-config-pubkey.pub`, `audit.db`, `vault.db`, `agents/<id>/identity.key`, `audit-alarms.log`); changes take effect at the next gateway start. A process the command starts holds the operator's principal. Every gateway socket takes a signed handshake, and every key it checks is one this process can reach: it can read the operator key and push a message to any channel and conversation through `orchestrator.sock` or answer pending approvals, including those for its own agent's later calls, through `gateway-permissions.sock`; register its own hook key in `hooks.db` and connect through `gateway-hooks.sock`; and read the agent identity and adapter keys that `gateway.sock` and `mcp-proxy.sock` check. The operator handshake on `orchestrator.sock` and `gateway-permissions.sock` is for attribution on the chain, every push and decision recorded against a verified key, and for refusing a same-UID process that does not hold the key; it is not confidentiality against a process that can read it. `wirken permissions approve` and the other authority-changing commands refuse under the `WIRKEN_EXEC` marker, which a command at that UID can clear. Its environment is an allowlist and its stdin is closed; nothing else separates it from the operator. Edit the file once; persists across restarts; gateway warns at startup. |
| `WIRKEN_ALLOW_UNVERIFIED=1` *(install-time only)* | The release-binary checksum and signature verification step in `install.sh`. The binary is installed on the strength of the network and the URL alone. Not honored at runtime; re-running `install.sh` is the only way to engage it. |

## NIST AI Risk Management Framework

Subcategory text is quoted verbatim from
[NIST AI 100-1](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.100-1.pdf),
Tables 1 to 4. Only subcategories whose text a shipped mechanism actually
satisfies are listed; most of the framework addresses organizational process
that a tool cannot discharge, and those are absent rather than mapped to
something adjacent.

A row is a claim about the mechanism, not a claim that an adopting
organization satisfies the subcategory. Four of the MEASURE entries below
qualify their scope with "as identified in the MAP function"; wirken does not
perform an organization's MAP function, so that qualifier stays the adopter's
to satisfy.

| Subcategory | Verbatim text | Mechanism | What it does not cover |
|---|---|---|---|
| GOVERN 1.7 | "Processes and procedures are in place for decommissioning and phasing out AI systems safely and in a manner that does not increase risks or decrease the organization's trustworthiness." | An ordered uninstall procedure that exports the audit chain before anything is destroyed, removes the service and scheduled entries before the binary they depend on, and enumerates the platform-side registrations and tokens that local deletion does not touch. [README](../README.md#uninstall), [channels.md](channels.md#platform-side-state) | Nothing automates it; the operator runs the steps. With a proxy archive, removing the data directory destroys the keys: the locked objects stay in the bucket and can no longer be read. |
| MAP 4.2 | "Internal risk controls for components of the AI system, including third-party AI technologies, are identified and documented." | Signature verification on third-party skill bundles and `mcp.json` entries, applied at install and again at every load; skills against the project registry root compiled in, or an operator root. [signing.md](signing.md) | The MCP gate has a documented opt-out, the skill gate only in a build without a compiled root, and a stdio MCP server whose entry sets `"sandbox": "off"` runs at the wirken UID with no process sandbox once spawned. |
| MEASURE 2.4 | "The functionality and behavior of the AI system and its components – as identified in the MAP function – are monitored when in production." | Every tool call and gate decision is a typed event written before the action, and each outcome, model reply and refusal one written after, forwarded by a polling forwarder to Datadog, Splunk HEC, Microsoft Sentinel or a webhook. [audit-cli.md](audit-cli.md), [siem-forwarder.md](siem-forwarder.md) | The legacy pipe drops a batch the endpoint refuses; the typed pipe sends it again. The local chain is the durable record. |
| MEASURE 2.6 | "The AI system is evaluated regularly for safety risks – as identified in the MAP function. The AI system to be deployed is demonstrated to be safe, its residual negative risk does not exceed the risk tolerance, and it can fail safely, particularly if made to operate beyond its knowledge limits. Safety metrics reflect system reliability and robustness, real-time monitoring, and response times for AI system failures." | The "fail safely" clause, on the dispatch path. `exec` is refused rather than run on the host when the sandbox is unavailable; an unregistered tool name resolves to Tier 3; a present-but-unparseable registry root refuses every skill; a ledger error under a block-mode budget refuses the call; a sidecar that cannot start refuses the `exec`. [sandbox-properties.md](sandbox-properties.md#no-silent-fallback), [permissions-and-identity.md](permissions-and-identity.md) | The rest of the subcategory. There is no regular safety evaluation, no residual-risk determination against a stated tolerance, and no safety metrics for reliability or failure response times. |
| MEASURE 2.7 | "AI system security and resilience – as identified in the MAP function – are evaluated and documented." | This document and [sandbox-properties.md](sandbox-properties.md), which pair each control with its gap and cite the symbol that implements it, plus the verification commands an operator can run to confirm the sandbox behaves as described. | Evaluation is by the maintainers against the code. No third party has assessed it. |
| MEASURE 2.8 | "Risks associated with transparency and accountability – as identified in the MAP function – are examined and documented." | A per-session hash chain with per-agent attestation, plus the documented limits of what it proves: that the signing key is held by the process that writes the chain, and that the default anchor is co-resident, so verification emits a warning naming what it does not establish. [audit-cli.md](audit-cli.md) | Tamper-evidence against a same-UID attacker needs an anchor held off the machine, which is the operator's to arrange. |
| MANAGE 2.4 | "Mechanisms are in place and applied, and responsibilities are assigned and understood, to supersede, disengage, or deactivate AI systems that demonstrate performance or outcomes inconsistent with intended use." | Org policy `blocked_tools` fails a named tool before dispatch; `wirken permissions revoke` drops a grant with immediate effect; `wirken sessions close` ends a session; `wirken preset unschedule` stops a scheduled agent; `wirken agents stop` holds an agent at once; `wirken proxy token revoke` refuses a proxy client from its next request. The operator is the approver, and every denial is recorded with the surface it came from. [enterprise.md](enterprise.md), [permissions-and-identity.md](permissions-and-identity.md) | Org-policy changes take effect at the next gateway start, so deactivation through that path is not immediate. There is no central registry or live revocation across instances. |

Subcategories wirken ships no mechanism for, including the whole of the
GOVERN function beyond 1.7, are deliberately absent.

## EU AI Act Article 14(4)

Point text is quoted verbatim from Article 14(4) of
[Regulation (EU) 2024/1689](https://eur-lex.europa.eu/eli/reg/2024/1689/oj),
Official Journal L of 12 July 2024. Its lead-in requires that "natural persons
to whom human oversight is assigned are enabled, as appropriate and
proportionate:". A row is here only where a shipped mechanism does what the
point says; points (b) and (c) have no wirken control and are absent. A row is
a claim about the mechanism, not a claim that a deployment meets the
Regulation. Ratings follow the ASI table above.

| Point | Verbatim text | Mechanism | Rating | Gap |
|---|---|---|---|---|
| 14(4)(a) | "to properly understand the relevant capacities and limitations of the high-risk AI system and be able to duly monitor its operation, including in view of detecting and addressing anomalies, dysfunctions and unexpected performance" | Monitoring: every action is a typed event written before it executes, on a per-session SHA-256 chain with signed chain heads ([audit-cli.md](audit-cli.md)), forwarded to a SIEM by a polling forwarder ([siem-forwarder.md](siem-forwarder.md)); `wirken sessions search` finds text across sessions ([audit-cli.md](audit-cli.md#wirken-sessions-search)). Anomalies: content carrying a stored secret is refused as a `leak_refused` row ([architecture.md](architecture.md#2-credential-lifecycle)); inbound messages matching extraction or override patterns emit `message.threat_flagged` (`InjectionDetector::scan`, `crates/gateway/src/injection_detect.rs`); the audit writer halts on repeated failed flushes or chain-verification passes, and `wirken run` does not start again until `wirken audit acknowledge --all` ([audit-cli.md](audit-cli.md#tamper-response)). Capacities and limitations are documented in [threat-model.md](threat-model.md) and this page; no mechanism conveys them. | Partial | Understanding is documentation, not a mechanism. Threat flagging records and does not block. Nothing detects drift whose individual calls each pass the gate. |
| 14(4)(d) | "to decide, in any particular situation, not to use the high-risk AI system or to otherwise disregard, override or reverse the output of the high-risk AI system" | At the action edge: every Tier 3 call prompts and runs only on approval (`ApprovalGate`, `crates/agent/src/approval_gate.rs`); a pending request is denied with `wirken permissions pending deny`; org `blocked_tools` fails a named tool before dispatch; an unregistered tool name is denied (`Action::UnknownTool`, `Agent::execute_tool`, `crates/agent/src/runtime.rs`). [permissions-and-identity.md](permissions-and-identity.md) | Partial | Nothing reverses a completed action: a call that ran stays done, and the chain records it. | 14(4)(e) | "to intervene in the operation of the high-risk AI system or interrupt the system through a ‘stop’ button or a similar procedure that allows the system to come to a halt in a safe state." | Intervene: the approval gates hold each Tier 3 call until the operator approves or denies it (`ApprovalGate`, `crates/agent/src/approval_gate.rs`). [sandbox-properties.md](sandbox-properties.md#processes-end-with-the-call) | Mitigated (with opt-out) | Under `sandbox.json` `mode: off`, a process the command started with `setsid` leaves the group and keeps running, and a command the operator approved can run `wirken agents stop` or `resume` itself. |
